# MCP server best-practice audit — 2026-08-04

Read-only audit of `tools/ast-dataflow/mcp-server.ts` against the mcp-builder skill rubric
(`SKILL.md`, `mcp_best_practices.md`, `node_mcp_server.md`, `evaluation.md`) plus the MCP
spec (2025-06-18) and SDK ^1.29. Conducted at extraction time per the DR-100 rider;
performed by a dedicated audit agent against main `aed1563` (pre-envelope-retrofit — see
the note at the end).

## TLDR

The server is protocol-correct on the wire — clean handshake, stdout carries only
JSON-RPC, no crashes, no write side effects — but has **two substantive defects**: an
unconstrained filesystem read that escapes `repoRoot` (HIGH-1), and an unschema'd `args`
object that silently accepts flags it then ignores and echoes back as if honoured
(HIGH-2). The root cause of most findings is **deprecated manual handler registration**
(HIGH-3): the server hand-rolls the low-level `Server` + `setRequestHandler` instead of
`McpServer.registerTool`, which would supply Zod validation, `-32602` on unknown tools,
`outputSchema`/`structuredContent` enforcement, annotations plumbing, and `tools/list`
pagination for free. The single-tool dispatch shape is NOT the problem (ratified design;
no defect found that argues for splitting it).

**Phase 4 of the rubric is wholly unmet: no evaluation exists.** Per `evaluation.md`, the
eval author must never have read the implementation, so it needs a clean-context agent.

LOW / hygiene: server name should be `ast-dataflow-mcp-server`; `corpus_info` should be
`ast_dataflow_corpus_info`; `serverInfo.version` hardcodes `1.0.0` vs package.json
`0.1.0`; raw `err.message` + absolute host paths exposed in responses; `tools/list`
ignores `cursor`; implicit `process.cwd()` binding is undocumented in the README
registration snippet; no cancellation/timeout (`extra.signal` unread — one slow query
blocks the serial queue); no MCP-side query examples / security section / performance
characteristics in README; `caveats` is ~19% of a typical response, repeated per call. The
rubric's `src/`+`dist/` build structure is a **justified deviation** (Bun-native package,
no build step). Unknown-tool-as-`isError` is defensible under `mcp_best_practices.md:229`
(rubric conflict with the web spec noted); resolves to the SDK default with HIGH-3.

## Verified OK

Handshake/negotiation; stdio hygiene (only JSON-RPC on stdout, banner on stderr); strict
TS, zero `any` in server/dispatch/staleness; DRY dispatch layer (`attachEnvelope` keyed by
`QueryName`); actionable error hints; resilience outside a TS repo (stays alive, retries);
reentrancy via the serial queue; symbol/file resolution bounded to the loaded corpus (the
read primitive is confined to the two sidecar args); every warm response carries staleness
`meta`.

## Not covered

Large-corpus behaviour (statSync sweep O(files), memory over long warm sessions,
pathological latency); concurrent calls; `notifications/cancelled`; protocol versions
beyond 2025-06-18; MCP Inspector; analytical correctness of the 15 queries; whether
`scope` can steer the ad-hoc Project in `fixture-uses.ts:314` outside repoRoot (read as
safe, not proven — **since measured, and it is NOT safe**: with `cwd` at the repo root,
tinyglobby returns host files for `../../*.json` and `/etc/*.conf`, and every discovered
`.json`/`.ts`/`.tsx`/`.md` is then read. Fixed with HIGH-1 under issue #1; the "read as
safe" verdict is the reason to prefer measurement over reading). Audit baseline was
pre-retrofit main `aed1563`; the envelope-retrofit merge (`85c7509`) landed after —
findings on caveats/envelope shape were re-read against it but measurements were not
re-run.
